What the Enshore IMS actually is, in one map

One Next.js application covering eleven business functions — quality, HSE, assets, documents, actions, people, risk, projects, lessons learnt, management review, and admin — all sat on a single Supabase backend. This page shows how a request moves through it, and how the modules actually depend on each other.

01

Infrastructure — where a request actually goes

Every page and every action in the IMS resolves to the same handful of hops. There is no separate backend service — Supabase and a handful of external APIs do all the work the Next.js app doesn't do itself.

02

Module map — how the eleven modules connect

The four columns are how work actually gets grouped — field operations, quality and risk, project delivery, and the governance layer everything else depends on. The arrows are the real, working dependencies: which modules raise actions, who supplies the people/document data every form uses, and what Admin gates.

→
Why Action Management and People Management sit apart from the three main zones: they aren't things a user "goes to work in" the way Quality or HSE is — they're the plumbing every other module runs through. A new module added to any zone gets action-raising and people-lookup for free by using the same shared components; it doesn't rebuild them.
